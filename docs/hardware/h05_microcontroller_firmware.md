# h05 — Microcontroller and Firmware

> **Building the schematic in KiCad?** See [`h05_mcu_schematic_build_guide.md`](h05_mcu_schematic_build_guide.md). SWD / flash footprint detail: [`h08_rp2350_flashing.md`](h08_rp2350_flashing.md).
>
> **How a sample gets from electrode to disk** — the dual-core split, DMA engines, the two USB pipes, the
> lock-free rings, and the back-pressure policy — is documented in
> [`h05_sensor_pipeline_architecture.md`](h05_sensor_pipeline_architecture.md). Read that first for the data-flow
> picture; this file is the reference for the pin map, PIO, register targets, protocol, and build/flash.

The RP2350A is the heart of the timing architecture. Everything that needs to happen with predictable latency happens here; everything else happens on the Pi 5. This document specifies the firmware's task model, PIO programs, USB protocol, and the host commands.

> **Transport note (production):** the binary record stream is carried on a **dedicated USB vendor
> bulk IN endpoint**, and **USB CDC** carries only text (commands, logs, replies). Sections below that say
> "USB-CDC" for the binary stream describe the earlier single-pipe design; the framing is identical, only the
> endpoint changed. See [`h05_sensor_pipeline_architecture.md`](h05_sensor_pipeline_architecture.md) §5.

## 1. Why RP2350A

| Feature | Why it matters |
|---------|----------------|
| Dual ARM Cortex-M33 at 150 MHz (or Hazard3 RISC-V) | One core is the time-critical sensor collector (producer); the other runs USB + housekeeping (consumer). No RTOS needed. FPU/DSP available on the M33 if we add on-MCU filtering. (Which physical core plays which role is fixed by the SDK — see §1.1.3.) |
| 520 KB SRAM (10 banks) | Generous ring buffers for EMG (31 B payload per sample in compact 48 B slots; 2048 slots ≈ 0.5 s at the default 4 kHz, ≈ 1.0 s at 2 kHz) and IMU, with comfortable headroom (2× the legacy RP2040). |
| 12 PIO state machines (4+4+4) | Deterministic microsecond-scale GPIO timing for the camera trigger and the WS2812 user LED, freeing CPU; one whole PIO block is spare. |
| Hardware timer (64-bit, 1 µs tick) | Direct source of `t_master_us`. No software counter overhead. |
| 30 GPIO + 2 SPI + 2 I2C + 2 UART | Plenty for ADS1299 + 2× IMU + trigger fan-out + UART debug + SWD. (Same 2-I2C limit as the RP2040 — the optional 3rd IMU still uses the PCA9546 mux, §1.1.2.) |
| 8 KB OTP + secure boot, SHA-256, TRNG | Not required in v1; available for signed-firmware, device serial, or RNG if a later revision needs it. |
| USB 1.1 device | USB-CDC at 12 Mbit/s; enough for ~1 MB/s of payload, against our ~220 kB/s budget (4 kHz EMG + dual IMU). |
| Free, well-documented, mainline | TinyUSB, pico-sdk (`PICO_PLATFORM=rp2350`), picoprobe debug; large community of biopotential + IMU example projects. |
| Cost | ~1 EUR / chip; the only cheaper MCUs are STM32G0/CH32V (less support, less PIO equivalent). |

Unlike the RP2040 (which has an internal LDO core regulator), the RP2350 core supply (**DVDD 1.1 V**) is generated by an **on-chip SMPS buck** that needs one external **3.3 µH** inductor plus a few capacitors ([`h05_mcu_schematic_build_guide.md`](h05_mcu_schematic_build_guide.md) Step 1.1, [`h07_power_grounding_safety.md`](h07_power_grounding_safety.md) §1).

We use the **chip directly** on the HAT, not a Pico 2 module. This is intentional: it lets us route the SPI to ADS1299 with minimum trace length and keeps the analog region cleaner. The Pico 2 (for which firmware is identical bit-for-bit) is used only as the development board during early firmware development.

### 1.1.1 Pin mux rationale (SPI0 EMG and GPIO budget)

The RP2350A maps each peripheral function to a **subset** of GPIOs (RP2350 datasheet, GPIO Bank 0 “Function Select” table — the same Bank-0 layout the RP2040 used, so this map carries over unchanged). The v1 map is **not** “use GPIO0–3 because lower numbers are special”; it is the intersection of valid alternate functions, HAT+ EEPROM pins, and leaving headroom for IMU/trigger/PIO.

**SPI0 (ADS1299).** Valid SPI0 pin sets include MISO on GPIO0/4/16/20, SCK on GPIO2/6/18/22, MOSI on GPIO3/7/19/23, and CS on GPIO1/5/17/21. We chose:

| Signal | GPIO | Why |
|--------|------|-----|
| MISO | **0** | SPI0_RX; short run to `emg` sheet. **GPIO0** is also HAT+ **`ID_SDA`** on the Pi side — only relevant if the HAT+ EEPROM is populated on this board ([`h02_hat_plus_schematic_build_guide.md`](h02_hat_plus_schematic_build_guide.md)); the custom HAT does not use GPIO0 for EEPROM in v1. |
| SCK | **2** | SPI0_SCK; avoids **GPIO1** (`ID_SCL` on HAT+). |
| MOSI | **3** | SPI0_TX. |
| /CS | **5** | SPI0 CS function; keeps **GPIO1** free (HAT+ ID / future strap). **GPIO4** is a valid SPI0 MISO but would duplicate a second RX pin — unused here. |
| DRDY / RESET / PWDN / START | **6–9** | Plain GPIO outputs/inputs; no SPI alternate required; grouped for layout next to the SPI cluster. |

Optional **22 Ω** series resistors on SCK/MOSI/MISO/**/CS** at the RP2350A damp ringing on the ADS1299 digital inputs ([`h05_mcu_schematic_build_guide.md`](h05_mcu_schematic_build_guide.md) Step 4 — **R18/R19/R20/R61**); they do not change the mux choice.

**I2C (BNO085).** The chip has **two** I2C controllers only. MTA on **I2C0** (GPIO20/21) and CRA on **I2C1** (GPIO18/19) gives each IMU a full **400 kHz** bus (~40 kB/s usable) for the ~26 kB/s SH2 budget ([`h04`](h04_imu_subsystem.md) §6). A third IMU (digitizing pointer, §1.1.2) shares **I2C1** through an optional **PCA9546** mux — not a third I2C peripheral.

**Panel I/O (v1):** GPIO4 (**LED_USER** addressable RGB), GPIO10 (**USER1**), GPIO11 (**USER2**), GPIO15 (**LED_HB**), GPIO24/25/29 (capture / fault / EMG lead-off 0603 LEDs) — see [`h05_mcu_schematic_build_guide.md`](h05_mcu_schematic_build_guide.md) §1.4 / Step 6. **Pi link** is **USB_DM/USB_DP** (dedicated), not I2C/SPI on the 40-pin header. **Still reserved:** GPIO1 (HAT+ `ID_SCL`); GPIO12/23 when optional DP IMU + mux are populated. **Pi↔MCU time sync** uses the USB **`pps`** command ([`s06`](../software/s06_time_synchronization.md)) — not a GPIO wire.

### 1.1.2 Optional digitizing-pointer (DP) IMU

The IEEE SENSORS 2025 jaw tracking system includes a **digitizing pointer (DP)** — a marker-equipped rigid pointer with known geometry, used during **landmark digitization** to register six dental points that define `CS_Mand^Anat` and `CS_Max^Anat` (paper §II.A, component (3)). That step is **optical** in the published system; OMoCap tracks DP markers, not an IMU.

For JTS-MM, an **optional third BNO085** on the DP handle is a reasonable extension:

- Records **pointer rigid-body attitude** on the same **`t_master_us`** time base as MTA/CRA IMU and EMG during the short digitization phase.
- Supports cross-checking optical DP pose (marker rigid-body fit / AprilTag cluster) vs. fused orientation.
- Does **not** replace optical landmark positions (tip contact still defines `P_Mand,i`, `P_Max,i`); it adds redundant attitude logging for calibration QA and future DP-only sessions.

**Default v1:** **DNP** — two IMUs (MTA + CRA) only; firmware and USB budget unchanged.

**When populated:** Mount a third Adafruit/SparkFun BNO085 breakout on a **12 × 10 mm pad** on the DP shaft (same mechanical pattern as MTA/CRA, [`h04`](h04_imu_subsystem.md) §3.4). Route a third **JST-SH 7-pin** cable (`J_IMU_DP`, pin 7 = shield → AGND) to the HAT. On the PCB, place **PCA9546A** (**H-IC-13**, DNP) on **I2C1**: **SC0 → CRA**, **SC1 → DP** (both devices may use address **0x4A** on separate mux channels). **GPIO18/19** remain the only I2C1 pins to the MCU; firmware selects the mux channel before CRA vs. DP transactions and handles **GPIO17** (CRA INT) and **GPIO12** (DP INT) separately. Shared **GPIO22** `IMU_NRST` resets all BNO085s. Mux performance notes: [`h04_imu_schematic_build_guide.md`](h04_imu_schematic_build_guide.md).

Report types **`0x17`–`0x19`** (`IMU_DP_QUAT`, `IMU_DP_RAW`, `IMU_DP_LIN_ACCEL`) mirror the MTA/CRA shapes; DP support is planned (not implemented in firmware or `jtsmm`); the record types are reserved.

### 1.1.3 Production DMA hot path (`firmware/jtsmm`)

Production firmware (`firmware/jtsmm`) implements the ISR/DMA model below on **dual cores** (no RTOS). Terminology:

| Term | Meaning |
|------|---------|
| **System master clock** | RP2350 `t_master_us` — every USB record carries this ([`01_architecture.md`](../01_architecture.md) §4) |
| **EMG sample epoch** | ADS1299 internal clock → `/DRDY` falling edge — hardware timing reference for EMG |
| **IMU sample epoch** | BNO085 internal scheduler → `/INT` falling edge per report — hardware timing reference for IMU |

**EMG (default):** `/DRDY` on **GPIO6**, polled by the sensor core (falling edge) → latch `t_master_us` → **SPI0 DMA** read of the RDATA command + **27 B** (3 status + 8×24-bit) via `spi_dma.c` → completion callback pushes `EMG_BLOCK` to the EMG ring buffer. No manual byte shifting on the CPU. At **4 MHz** SPI (`mcu.platform.spi0.hz`), the 28-byte transfer takes ≈ **56 µs** — well inside the 250 µs period @ **4 kHz** acquisition.

**IMU (default — `sync.mode: int_driven`):** `/INT` on **GPIO16** (MTA) / **GPIO17** (CRA) → separate ISRs → **I2C0/I2C1 DMA** SHTP read (`i2c_dma.c`) on each IMU's dedicated bus. Buses run **in parallel** with SPI0 EMG DMA.

**IMU (optional — `sync.mode: emg_drdy_divisor`):** When IMU rate evenly divides EMG rate (e.g. 1000 Hz EMG + 250 Hz IMU → divisor 4), the polled DRDY service in the sensor loop counts edges and kicks I2C DMA on every *N*th one. Host `validate.py` rejects non-integer divisors. See [`h04_imu_subsystem.md`](h04_imu_subsystem.md) §6 and [`s08_runtime_configuration.md`](../software/s08_runtime_configuration.md) §`mcu.imu_*`.

**PIO (not I2C):** `trigger_gen` on **GPIO13**, WS2812 on **GPIO4** (the Track A sync LED on **GPIO14** is timer-driven) — deterministic GPIO timing; BNO085 stays on hardware I2C + DMA in v1.

**Core assignment** (implemented in `src/app/sensor_core.c` + `comms_core.c`). The production firmware uses a
**polled DMA** model, not an ISR-per-sample model: each core runs a tight super-loop that kicks and services
DMA transfers. The file names track the **logical roles**; the **physical** RP2350 core is fixed by the Pico
SDK (`main()` is always physical core 0; `multicore_launch_core1()` starts physical core 1):

| Logical role | File | Physical core | Work |
|--------------|------|---------------|------|
| **Sensor core** (sole producer) | `sensor_core.c` | **core 1** | Poll DRDY → kick/service **SPI DMA** (EMG 27 B); kick/service **I2C DMA** (IMU SHTP); PIO `TRIGGER_EVENT`; lead-off poll; **only** writer of the EMG/IMU/event rings |
| **Comms core** (sole consumer) | `comms_core.c` | **core 0** | Drain SPSC rings → `host_link` **USB vendor bulk** TX; `cmd_parser`/`config_apply` on **CDC**; panel; 1 Hz heartbeat + `REC_STATS` + sensor-health watchdog |

Inter-core communication uses DMA-backed SPSC ring buffers — **no mutex** on the hot path (one producer on the
sensor core, one consumer on the comms core; `__dmb()` barriers only). Full detail and the physical-vs-logical
naming table: [`h05_sensor_pipeline_architecture.md`](h05_sensor_pipeline_architecture.md) §3–§4.

## 2. Task model

Two cores, no RTOS. The production firmware uses a **polled DMA** super-loop on each core (not an ISR per
sample): the sensor core kicks DMA transfers and services their completion in a tight loop, which gives the
same low latency as ISRs while keeping the buses collision-free and the code easy to reason about. The work is
partitioned for determinism. (Terminology reminder: the sensor core lives in `sensor_core.c` but runs on
**physical core 1**; the comms core lives in `comms_core.c` on **physical core 0** — see §1.1.3.)

### Sensor core (`sensor_core.c`, physical core 1) — sole producer

A tight loop (`sensor_core_poll()`) that, each iteration:

- Services EMG first (twelve times per loop): poll `/DRDY`, and when a sample is ready kick a **SPI0 DMA** read
  of the RDATA command + 27 bytes (3 status + 8 × 24-bit). The DMA moves the bytes; the CPU only stamps
  `t_master_us` and pushes the `EMG_BLOCK` into the EMG ring on completion. At 4 MHz SPI the 28-byte transfer
  is ~56 µs — well inside the 250 µs period at the default 4 kHz. A wedge watchdog (~2 ms) aborts and re-arms a stuck transfer.
- Services both IMUs: kick/complete non-blocking **I2C0/I2C1 DMA** SHTP reads on each IMU's dedicated bus,
  pushing quaternion reports into the per-slot IMU rings. An **8 ms I2C DMA wedge watchdog** (`i2c_dma_service`)
  aborts stuck transfers so a hung bus cannot block the other slot.
- Polls ADS1299 lead-off status once per second, and **only when the SPI DMA is idle**, so a register read
  never collides with an in-flight EMG frame.

This core never touches USB and never blocks on I/O.

### Comms core (`comms_core.c`, physical core 0) — sole consumer

A loop that each iteration pumps USB (`tud_task()`), drains the SPSC rings to the **USB vendor bulk IN**
endpoint via `host_link` (IMU/events before EMG — see the back-pressure policy in
[`h05_sensor_pipeline_architecture.md`](h05_sensor_pipeline_architecture.md) §6), and handles one CDC
command / `config apply` step. Once per second it emits `HEARTBEAT` and a `REC_STATS` record (drop counters,
loop rates) and runs the sensor-health watchdog. If an IMU slot's ring push count is flat for **3 s** while
streaming, the comms core calls **`imu_slot_recover()`** (SHTP soft-reset + re-enable reports). Lead-off/PPS
handling is folded into this cadence.

Inter-core communication uses DMA-backed SPSC ring buffers; no locks are needed because each ring has exactly
one producer (sensor core) and one consumer (comms core).

## 3. USB protocol

Binary records travel on the **USB vendor bulk IN** endpoint; text commands, log lines, and replies travel on
**USB CDC**. The frame format below is identical on both (only the endpoint differs from the earlier
single-CDC design). See [`h05_sensor_pipeline_architecture.md`](h05_sensor_pipeline_architecture.md) §5 for why
the two pipes are separated.

### 3.1 Frame format

```
+--------+--------+--------+--------+
| 0x55   | 0xAA   | TYPE   | LEN    |
+--------+--------+--------+--------+
|  T_MASTER_US (8 bytes, LE)        |
+--------+--------+--------+--------+
|  PAYLOAD (LEN bytes)              |
+--------+--------+--------+--------+
|  CRC16 (2 bytes, LE)              |
+--------+--------+--------+--------+
```

- `0x55 0xAA` — sync word. Receivers resync to the next occurrence after any framing error.
- `TYPE` — record type (table §3.2).
- `LEN` — payload length in bytes (`0..240`).
- `T_MASTER_US` — 64-bit `uint64_t`, microseconds since MCU boot, little-endian.
- `PAYLOAD` — TYPE-specific.
- `CRC16` — CCITT, polynomial `0x1021`, init `0xFFFF`, computed over `TYPE..PAYLOAD` (does **not** include the sync word).

Maximum frame size: 4 + 8 + 240 + 2 = 254 bytes — fits in a single USB Full-Speed bulk transfer.

### 3.2 Record types

| Code | Name | LEN | Payload |
|------|------|-----|---------|
| 0x10 | `EMG_BLOCK` | 31 | ADS1299 status (3 B) + 8× 24-bit channel data (24 B) + `uint32` LE `seq`: acquisition sequence number, +1 per conversion; conversions the firmware knows it lost advance it too, so a seq gap on the host is the total loss after the ADC (wraps at 2³²). Firmware before 2026-09 sends 27 B without `seq`. |
| 0x11 | `IMU_MTA_QUAT` | 17/18 | `uint8` report_id + 4× `float32` `w,x,y,z` + optional `uint8` accuracy. |
| 0x12 | `IMU_MTA_RAW` | 7/8 | `uint8` sensor_id (accel/gyro/mag) + 3× `int16` + optional `uint8` accuracy. |
| 0x13 | `IMU_MTA_LIN_ACCEL` | 12/13 | 3× `float32` linear accel m/s² + optional `uint8` accuracy. |
| 0x14 | `IMU_CRA_QUAT` | 17/18 | same shape as IMU_MTA_QUAT |
| 0x15 | `IMU_CRA_RAW` | 7/8 | same shape as IMU_MTA_RAW |
| 0x16 | `IMU_CRA_LIN_ACCEL` | 12/13 | same shape as IMU_MTA_LIN_ACCEL |
| 0x17–0x19 | `IMU_DP_*` | — | Reserved for the optional digitizing-pointer IMU ([§1.1.2](#112-optional-digitizing-pointer-dp-imu)); not implemented in firmware. |
| 0x20 | `TRIGGER_EVENT` | 12 | 4× `uint8` flags (4 B) + 1× `uint64` `trigger_id` (8 B). `flags[0]` = stamp source (`1` PIO IRQ at the exposure-start edge, `2` software timer, `0` firmware before 2026-09), `flags[1]` = timer-watchdog fallback engaged. | 0x21 | `LED_FLASH_EVENT` | 4 | 1× `uint32` `flash_id`. The frame header `t_master_us` is the LED-on edge time; the Pi pairs it with the camera frame that observed the flash (see [`h06_synchronization.md`](h06_synchronization.md) §4.2). |
| 0x30 | `HEARTBEAT` | 16 | `uint32` TX bytes, `uint32` missed_drdy, `uint64` applied-config fingerprint. |
| 0x40 | `PPS_REPLY` | 8 | 1× `uint64` echoed host PPS request id. |
| 0x50 | `ADS_STATUS` | — | Reserved, not emitted (lead-off bits travel in the `EMG_BLOCK` status bytes). |
| 0x51 | `STATS` | 144 | 36× `uint32` LE counters, once per second and on `stats` (hosts decode by count; older firmware sends 28). See the field list below. |
| 0x70 | `LOG` | 0–240 | ASCII log message. |
| 0xE0 | `CMD_ACK` | 1 | 1 = success, 0 = failure. |

**`STATS` fields** (index: name; append-only, mirrored by `STATS_FIELDS` in `protocol/records.py` and the native module):
0 `drdy_count`, 1 `missed_drdy`, 2–9 ring `push`/`drops` for EMG, IMU MTA, IMU CRA, events, 10 `usb_tx_bytes`
(since boot), 11 `sensor_loop_hz`, 12 `comms_loop_hz`, 13 `tx_drops`, 14 `max_drdy_gap_us`, 15 `imu_svc_max_us`,
16 `leadoff_max_us`, 17 `leadoff_count`, 18 `poll_max_us`, 19 `frame_misalign`, 20 `emg_misalign_drops`,
21 `misalign_max_streak`, 22 `emg_resyncs`, 23 `spi_wedges`, 24 `trig_pio_events`, 25 `trig_timer_events`,
26 `imu_i2c_aborts`, 27 `imu_cra_i2c_aborts`, 28 `tx_drops_emg`, 29 `tx_drops_imu`, 30 `tx_drops_other`,
31 `imu_mta_seq_gaps`, 32 `imu_cra_seq_gaps`, 33 `imu_mta_resets`, 34 `imu_cra_resets`, 35 `stats_seq`
(1 = first record after boot). Ring `*_drops` are losses inside the MCU (ring full); `tx_drops*` are frames
lost at the USB boundary (reset at each EMG stream start).

### 3.3 Host → MCU commands

**Production** (`firmware/jtsmm`, `cmd_parser.c`): text lines terminated with `\n`. Session start uses **`config apply`** (one JSON line); bench/debug uses the commands below.

| Command | Effect |
|---------|--------|
| `info` | Firmware version string `jtsmm <version>-prod (RP2350 production)` and the last reset reason (`<version>` from `include/jtsmm/version.h`; 1.1.0 since 2026-11-04, firmware README "Version") |
| **`config apply <json>`** | **Primary** — the whole JSON is parsed and validated first; only then are running streams (EMG, IMU, trigger — logged) stopped, the sensor core parked and the config applied (`platform` → `emg` → `imu_mta` → `imu_cra` → `trigger`). Replies `CMD_ACK` + `config apply OK`, or `config apply FAIL (<reason>)`; a config that fails validation leaves the running one untouched. While an apply runs, any `config apply/init/load` replies exactly `config apply BUSY` |
| `config init` | Same path with factory defaults; replies `config init OK\|FAIL` |
| `config dump` | Print resolved MCU config JSON. Every parsed key is written back, so it round-trips through `config save`/`config load` (flash) and a saved config re-applies identically after a power-cycle. |
| `config save` / `config load` / `config erase` | Persist / re-apply / delete the dumped config in the last flash sector. Save and erase are **refused while EMG, IMU or the trigger run** (`FAIL (<reason>)`); core 1 is locked out of flash during the write. At boot a saved config that fails is replaced by factory defaults (logged). |
| `platform_status` | RP2350 clocks, buses, buffer fill, drops |
| `ads_status` | ADS1299 registers + active SPI speeds. **Refused while EMG is streaming** (see note below); `ads_status force` overrides |
| `ads_regs` | ID, CONFIG1–3, CH1/CH7/CH8SET and BIAS_SENSP/N with their expected values — confirms `--bias-drive` / `--bias-channels` / `--active-channels` reached the chip. Same streaming rule as `ads_status` |
| `ads_start` / `ads_stop` | Start/stop EMG streaming to USB; `ads_start` is refused when `emg.enabled` is false (`ads_start` calls `host_link_reset_tx_stats()` when EMG was idle, so per-session `tx_drops` start at zero) |
| `imu_stream mta\|cra on\|off` | Enable/disable IMU reports for a slot |
| `imu_status` | Per-slot IMU state: enable/stream/int flags, achieved I²C rate + read timing, and BNO085 on-chip **calibration accuracy** (`cal quat=… accel=… gyro=… mag=…`, `0=unreliable..3=high`). **Refused while EMG is streaming**; `imu_status force` overrides |
| `imu_savecal` | Persist each idle slot's BNO085 dynamic calibration to flash (SH-2 *Save DCD*) so it survives a power-cycle; stream must be **off** ([`cv02` §7.1](../calibration_validation/cv02_imu_calibration.md#71-on-chip-bno085-dynamic-calibration)). Whether the dynamic calibration keeps running during a take is the per-slot config `dynamic_calibration` (default on; [`cv02` §7.2](../calibration_validation/cv02_imu_calibration.md)) |
| `trig_start [rate_hz] [pulse_width_us]` / `trig_stop` | Arm/disarm PIO trigger. Bare `trig_start` uses **resolved** `mcu.trigger` settings; optional args override rate and/or pulse width for this start only (polarity still from config). Refused (`trig_start FAIL (<reason>)`) unless rate is 1–200 Hz and 0 < width < period (a too-long width used to be halved silently), and when `trigger.enabled` is false. Host wrapper: `jtsmm trigger` (trigger-only — does **not** apply config or start EMG/IMU) |
| `trig_status` | Running flag, `trigger_id`, stamp mode (configured/active/fallback), compensation state, `period_us` vs `pin_period_us`, which edge is stamped, and counters `pio_pulses` / `timer_events` / `spurious_irq` |
| `trig_stamp [pio\|timer]` | Select how `TRIGGER_EVENT` is timed: `pio` (default) latches in the PIO IRQ at the pulse edge; `timer` is the legacy software timer. Applies at the next `trig_start`; resets to `pio` on power-cycle |
| `trig_comp [on\|off]` | PIO cycle-overhead compensation (default **on**; pin period == `period_us`). `off` reproduces the pre-2026-09 pin period (`period_us + 5`) for a scope A/B. Applies at the next `trig_start` |
| `selftest` | Bench self-test gate ([`h03`](h03_emg_frontend.md) §13). Calls `ads1299_init()`, probes both IMUs and re-inits the trigger PIO, so it is **refused while EMG or an IMU streams (or recovers) or the trigger runs**; `selftest force` overrides |
| `emg_guard [drop on\|off] [resync on\|off]` | Show or toggle the EMG framing guard, and print its counters (`misaligned`, `dropped`, `worst_streak`, `resyncs`, `spi_wedges`). Both knobs default **on**: misaligned frames are dropped, and a sustained slip triggers an SPI/DMA + `SDATAC` resync |
| `led rgb <r> <g> <b>` | WS2812 **LED_USER** bench colour |
| `pps <id>` | Host↔MCU clock handshake: replies `PPS_REPLY{id}` stamped with `t_master_us` at parse time. `jtsmm record` sends `host.capture.pps_samples` (default 8) at the start and end of a take and fits Pi `CLOCK_MONOTONIC` → master (`sync/report_json.pi_to_master`), which is what lets it cross-check each camera frame's `SensorTimestamp` against the trigger it was paired with |

**Bus ownership:** while EMG is streaming, SPI0 (ADS1299) and the IMU I²C buses belong to the **sensor core**, with no mutex against the comms core. `ads_status`, `imu_status`, `selftest` and `ads_drdy_watch` therefore refuse by default — running them mid-stream retimes SPI0 to the config baud and toggles CS during an in-flight DMA transfer, which slips the RDATA byte stream and fills the EMG trace with full-scale hash (counted as `frame_misalign`). Append `force` only on the bench; it logs a warning to both CDC and the record stream. `config apply` is safe because it calls `sensor_core_stop()` first.

**Host session sequence** (`jtsmm record`, since 2026-09): `config apply` → `ads_start` → `imu_stream mta on` + `imu_stream cra on` → settle → `pps` ×8 → **cameras start** → `trig_start` (so pulse 1 is the cameras' first frame; `host.capture.trigger_after_cameras: false` restores the old trigger-first order) → record → `pps` ×8 → `trig_stop` → `imu_stream … off` → `ads_stop`.

Panel LEDs are updated in the heartbeat task and ISRs (capture / IMU activity / lead-off); see [`h05_mcu_schematic_build_guide.md`](h05_mcu_schematic_build_guide.md) Step 6.

### 3.4 ADS1299 power-up sequence (per SBAS499 §11.1)

`ads1299_init()` must honor the datasheet power-up timing, which is gated by the **100 µF on VCAP1** ([`h03`](h03_emg_frontend.md) §9):

1. On HAT power-up, keep all digital/analog inputs (incl. `CS`, `START`, `RESET`, `PWDN`) low until the 3.3 V rails are stable.
2. Start the master clock (`CLK`); the RP2350A supplies it once supplies have settled.
3. Hold off issuing `RESET` until **tPOR (2¹⁸ × tCLK ≈ 128 ms) _or_ VCAP1 > 1.1 V, whichever is longer**. The firmware waits **≥ 150 ms after `PWDN` goes high** (SBAS499C typ. "power-up to DRDY low" 150 ms) before the first reset pulse, then holds `RESET` low ≥ `tRST`.
4. Release `RESET`, then program the configuration registers (gain, `fs`, bias/DRL — see table below).
5. `/PWDN` is held high for normal operation (GPIO8).

**ADS1299 bias / DRL register targets (as-built hardware, [`h03`](h03_emg_frontend.md) §5):**

| Register / field | Value | Reason |
|------------------|-------|--------|
| `CONFIG3.PD_REFBUF` | **1** | Enable internal **4.5 V** reference buffer (SBAS499 Table 15) |
| `CONFIG3.PD_BIAS` | **1** | Bias amplifier powered → `CONFIG3 = 0xEC` with bias on, `0xE0` off |
| `CONFIG3.BIASREF_INT` | **1** | Internal (AVDD+AVSS)/2 = 2.5 V bias reference. The `BIASREF` pin is tied to AGND, so `0` (`0xE4`) would drive the body to the 0 V rail (SBAS499C §10.1.3) |
| `CONFIG3.BIAS_STAT` | read-only | Masked in every CONFIG3 readback check |
| `CONFIG4.PD_LOFF_COMP` | **1** when lead-off is on | `1` = comparators **enabled** (`CONFIG4 = 0x02`, SBAS499C §10.1.2.1); `0x00` when lead-off is off |
| `LOFF_STATP/N` (0x12/0x13) | CH1–CH6 only | Firmware publishes only bits also set in `LOFF_SENSP/N` and never CH7/CH8 (no patient pin / DRL) |
| `CONFIG3.BIAS_MEAS` | **0** (normal) / **1** (bench) | **0** for acquisition; **1** only when routing BIAS to CH7 for debug |
| `BIAS_SENSP` / `BIAS_SENSN` | CH1–CH6 enabled | CH7/CH8 excluded from bias derivation |
| `CH7SET` | **0x81** (PD=1, input shorted) | No patient pin — powered down; optional BIAS readback (`MUX = 010`) is bench-only |
| `CH8SET.MUX` | **111** | Route internal **BIASIN** to **IN8N** (DRL patient path, Fig. 33) |
| `CH8SET` | **0x67** bias on / **0x60** DRL probe / **0x81** otherwise | Powered only when it carries the DRL (or the `emg check` probe) |

After programming, the firmware reads back **every** register it wrote (read-only bits masked) and fails `config apply` with `ads init FAIL: reg 0x.. wrote 0x.. read 0x..` on any mismatch; `ads_start` is refused until an init succeeds.

> The fixed startup delay is intentionally generous; trimming it requires measuring the actual VCAP1 ramp on the bench (covered by the [`h03`](h03_emg_frontend.md) §13 self-test).

## 4. PIO programs

PIO drives the camera trigger (§4.1) and the WS2812 user LED (§4.4); the sync LED is timer-driven (§4.3).

### 4.1 `trigger_gen`

Generates the camera trigger ([`pio/trigger_gen.pio`](../../firmware/jtsmm/pio/trigger_gen.pio)). The PIO clock is 1 MHz; the CPU loads two templates once per `trig_start`: the **low phase = `pulse.width_us`** (IMX296 exposure) and the **high phase = period − width**. The fixed per-phase instruction overhead is subtracted in `trigger_timing.c`, so the pin period equals `period_us`.

```asm
.wrap_target
    mov y, x             side 1   ; reload high, pin HIGH
pulse_high:
    jmp y--, pulse_high
    irq set 0            side 0   ; pin LOW + raise IRQ flag 0 (exposure start)
    mov y, isr                    ; reload low
delay_low:
    jmp y--, delay_low
.wrap
```

`irq set 0` fires on the exposure-start edge. `trigger_pio.c` stamps `t_master_us` and increments `trigger_id` in that IRQ (edges lost to a late IRQ still advance the id), then emits `TRIGGER_EVENT`.

### 4.2 `pps_capture`

Not implemented: there is no GNSS 1 PPS PIO program (no GNSS wire on the v1 HAT). **Do not confuse** with the Pi **`pps <id>`** USB command — that is a software timestamp handshake.

### 4.3 `led_flash`

Drives the sync LED (GPIO14) for the Track-A LED-flash synchronization protocol from a `repeating_timer` plus a one-shot alarm for the LED-off edge; `pio/led_flash.pio` exists but is unused. `flash on` starts a **repeating** flash train (default **1 Hz**, 200 µs pulse width — both configurable); `flash off` stops it. On **each** pulse the firmware latches the LED-on edge time and emits a `LED_FLASH_EVENT` (TYPE 0x21) record carrying a monotonic `flash_id`, with the edge `t_master_us` in the frame header. The Pi pairs each `LED_FLASH_EVENT` with the camera frame that observed that flash (see [`h06_synchronization.md`](h06_synchronization.md) §4). A one-shot mode (`flash once`) emits a single pulse for manual checks.

### 4.4 User RGB LED (`LED_USER`)

**Hardware:** one **WS2812B-2020** addressable RGB LED (**H-PAS-09**, catalog) on **GPIO4** — schematic ref **LED_USER**, footprint **`LED_SMD:LED_WS2812B-2020_PLCC4_2.0x2.0mm`**. **VDD** on **`+5V_IN`** (Pi header **5 V**); **DATA** from **GPIO4** (~3.3 V) via **R25** (220 Ω) — see [`h05_mcu_schematic_build_guide.md`](h05_mcu_schematic_build_guide.md) Step 6 §6.1). Same idea as the single RGB indicator on many **ESP32-S3** dev boards (NeoPixel-style, one-wire serial colour).

**Why not a 0603 LED + resistor?** The other panel indicators (**LED_HB**, **LED_FAULT**, etc.) are ordinary **0603** LEDs: one GPIO, one fixed colour, **470 Ω–1 kΩ** series resistor. A **programmable** colour needs either **three PWM channels** (RGB discrete LEDs) or a **smart LED** with an integrated controller. We use the latter so **GPIO4** stays a **single** data pin.

**Firmware** (`src/drivers/panel.c`, `pio/ws2812.pio`):

- The LED is driven by a **PIO WS2812** bitstream (800 kHz) and shows the firmware state: green = idle, amber = armed, red = fault (same condition as **LED_FAULT**); while streaming, a colour mixed from the active streams (EMG, IMU, trigger).
- Host command `led rgb <r> <g> <b>` for arbitrary bench colours during bring-up.
- **USER2** (**GPIO11**): when **not streaming** (no EMG/IMU/trigger active), a press starts **LED disco mode** — all panel LEDs + RGB cycle for **~15 s** (`panel_disco_tick()` on the comms core). Ignored while streaming.
- All colours are scaled to about 25 % of full brightness, and dimmed further when several streams are active; a dim LED limits EMI near the EMG front-end.
- **Colour order:** **GRB** (WS2812B default).

**Layout:** **top-mount** **2020** on the **panel side** of the PCB (bottom **L4** in this HAT); lens points toward the user. Keep the **DATA** trace short. **LED_HB** is a separate **0603** on **GPIO15**. See Step 6.

## 5. Buffer sizing

Worst-case data rates and 1-second buffer requirements:

| Stream | Rate (acquisition default) | Bytes/record | Bytes/s | Ring buffer (production default) |
|--------|----------------------------|--------------|---------|----------------------------------|
| EMG | **4 kHz** (`emg.profile: acquisition`) | 45 (header + 31 B payload + CRC) | 180 kB/s | `mcu.platform.buffers.emg_ring` byte budget (98304 B = 2048 compact slots ≈ 0.5 s) |
| IMU MTA quat | **390 Hz** (`kinematics_accel`, ~350 with a 250 Hz vector active) | 32 | 12.5 kB/s | `imu_ring` per slot |
| IMU MTA lin accel | 250 Hz (~220 measured) | 27 | ~7 kB/s | same |
| IMU CRA × 2 reports | same as MTA | — | ~19 kB/s | same |
| Triggers | 30 Hz (`imx296_dual_csi`) | 26 | 0.8 kB/s | `event_ring` |
| Heartbeat | 1 Hz | 30 | 0.03 kB/s | 1 kB |
| Total @ acquisition | | | **~220 kB/s** | configurable via `mcu.platform` |

**`high_rate`** is also 4 kHz EMG, so the budget stays ~220 kB/s — well under the USB Full-Speed ~1 MB/s (2 kHz: ~130 kB/s).

The RP2350A has **520 KB SRAM**; the ring buffers take ≈144 KB (2048 compact EMG slots, 3 × 64 full slots; the whole firmware uses ≈222 KB of static RAM), leaving ample room for stack, USB descriptors, and firmware globals. (The legacy RP2040 had only 264 KB, which made the same allocation tight; the extra SRAM is one of the reasons for the RP2350A.)

## 6. MCU alternatives

| MCU | When to use it |
|-----|----------------|
| **RP2350B** | Same die as the RP2350A but in the QFN-80 package with 48 GPIO. Use only if a future revision needs more than the 30 GPIO of the QFN-60; it does **not** add a third I2C controller. |
| **RP2354A** | RP2350A with 2 MB stacked QSPI flash in-package — lets you delete the external W25Q flash (H-IC-06). Drop-in for the firmware (same `rp2350` platform). |
| **RP2040** (legacy) | The prior MCU: dual M0+ @133 MHz, 264 KB SRAM, internal-LDO core (no inductor). Use only as a stock fallback; firmware is identical except the pico-sdk platform (`rp2040`) and it halves the SRAM headroom. |
| **STM32F4 / F7** | Use if a labs's policy demands ST tools, or if there's an existing STM32 firmware base to reuse. Firmware would need a partial rewrite; the task model is portable. |
| **Teensy 4.x (NXP i.MX RT)** | Excellent performance and Arduino ecosystem; downside is the Teensy is a module, harder to integrate into a custom PCB economically. |
| **ESP32-S3** | Rejected: RF noise on the analog board is unacceptable for a sub-µVrms front-end. |

## 8. Logging and diagnostics

The firmware emits `LOG` records (TYPE 0x70) at startup, on configuration changes, and on error. These show up on the Pi side as Python `logging` messages. There is no on-MCU file system; persistent logging is the Pi's job.

A `--debug` build adds verbose logging (e.g. SPI byte dumps for the first 100 ADS1299 transactions). The debug build does not fit in the production buffer budget; it is for bring-up only.

## 9. Failure handling

The firmware is designed to **fail safely**, not silently:

- USB stall / disconnect → continue running locally; a full ring drops the **newest** record (`*_drops`), and with no host mounted records are discarded at the USB boundary (`tx_drops*`). Both counters are in `REC_STATS`.
- ADS1299 DRDY missed → counted in `missed_drdy`; if sustained, the FAULT LED latches and a `REC_LOG` (`watchdog: sustained missed_drdy`) is emitted (advisory; the ADS1299 is not restarted).
- IMU SHTP error (CRC mismatch or unexpected packet) → reset the SHTP transport. Sustained stall (no ring pushes for 3 s) → **`imu_slot_recover()`** on the comms core (I2C DMA abort + BNO085 soft-reset).
- Bad command → CDC commands are text: an unknown line answers `unknown: <line>`; a refused or failed command answers `<cmd> FAIL` / `<cmd> REFUSED` (+ `CMD_ACK` 0).
- Hard fault (either core) → `isr_hardfault` blinks SOS on **LED_FAULT** forever (RAM-resident, no IRQs). No fault frame is saved yet.

**Hardware watchdog — off by default** (not yet validated on the PCB). Build with `-DJTSMM_WATCHDOG_MS=4000` to enable it: the comms loop kicks it only while core 1 also makes progress (or is parked on purpose), config apply / flash writes / `selftest` / `imu_savecal` stretch it to 15 s, and a hang or hard fault resets the MCU. Every boot prints `boot: last reset = …` (also in `info`); after a watchdog reset it is logged as a `REC_LOG` and the FAULT LED is latched.

## 11. Versioning

Firmware version follows semantic versioning (`MAJOR.MINOR.PATCH` in `include/jtsmm/version.h`). `info` returns `<version>-prod` (§3.3); the string carries no git hash. The host preflight of `jtsmm record` compares the firmware version against its expected range (`hat.firmware_version`, `>=1.0.0,<2.0.0` in `software/jtsmm/etc/jtsmm.yaml`) at session start and reports a version outside it as a preflight error, which stops the recording unless the quality gate is switched off (helps catch the operator-grade mistake of running an old firmware after pulling the latest software).
